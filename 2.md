# StudyGenius — SVG Scientific Visual Rendering Master Specification

**Status:** MASTER SPECIFICATION — obbligatoria per il sottosistema di rendering visuale  
**Ambito:** grafici scientifici, mappe concettuali, schemi tecnici, P&ID/PFD/BFD, diagrammi, figure formula-derived, visuali source-reconstructed e artifact SVG destinati al PDF finale  
**Rapporto con gli altri documenti:** questa specifica è complementare a `STUDYGENIUS_VISUAL_SYSTEM_MASTER.md`. Quest'ultimo governa la chain of custody, Visual Coverage, commitments, QA e persistenza end-to-end; questo documento governa **come un visuale accettato deve essere progettato, renderizzato, salvato, inserito, esportato e verificato a livello grafico/editoriale**.

---

# 0. Direttiva assoluta

Questo file non deve essere interpretato come un elenco di librerie da installare ciecamente.

Google Anti-Gravity ha libertà di:

- scegliere stack;
- scegliere librerie;
- cambiare renderer;
- progettare contratti migliori;
- riutilizzare componenti già presenti;
- evitare dipendenze inutili;
- preferire soluzioni deterministiche;
- proporre una soluzione superiore a quella qui descritta.

Non ha libertà di ignorare il risultato finale richiesto.

Il risultato richiesto è:

> **StudyGenius deve saper produrre visuali scientifici vettoriali di qualità editoriale, coerenti con gli esempi di riferimento, realmente leggibili in PDF A4, riproducibili, scaricabili come artifact, verificabili e integrati con il sistema di Visual Commitment.**

Una demo isolata non è sufficiente.

Un SVG bello aperto nel browser non è sufficiente.

Un `VisualSpec` corretto non è sufficiente.

Un grafico deve arrivare realmente nel PDF finale e risultare leggibile alla dimensione reale di stampa.

# 1. Standard qualitativo di riferimento

I PDF di riferimento forniti con il progetto definiscono il livello desiderato.

Non devono essere copiati pixel per pixel.

Devono essere interpretati come **golden references di qualità e grammatica visuale**.

## 1.1 Mappa concettuale vettoriale

La mappa di Chimica Fisica mostra il comportamento desiderato:

- vero diagramma vettoriale;
- gerarchia leggibile;
- blocchi distinti;
- frecce pulite;
- percorsi concettuali espliciti;
- nessun ASCII;
- nessuna struttura tipo filesystem;
- densità limitata;
- testo breve dentro i nodi;
- raccordo finale tra rami concettuali.

La mappa collega:

```text
Fenomeno macroscopico
↓
Modello microscopico
↓
Coordinata di reazione / PES
↓
biforcazione
├─ Arrhenius
└─ Eyring TST
↓
Raccordo finale
```

Questo è un esempio di **diagramma semantico**, non di tabella travestita da mappa.

## 1.2 Figura tecnica scientifica

Il profilo energetico della reazione mostra uno standard diverso:

- assi scientifici;
- curve chiaramente differenziate;
- etichette direttamente collegate agli oggetti;
- marker sui punti fisicamente importanti;
- frecce per le barriere energetiche;
- annotazione di `Ea`, `ΔH`, intermedio e stato di transizione;
- caption esplicativa;
- guida alla lettura dopo il grafico.

Il sistema deve comprendere che questa figura richiede un renderer scientifico e non un renderer di knowledge graph.

## 1.3 Grafico a regioni indipendenti

L'esempio Arrhenius mostra una composizione ad alta densità:

- regione principale del grafico;
- pannello risultati;
- diagnostica residui;
- bande di confidenza;
- punti sperimentali;
- barre d'errore;
- regressione;
- takeaway didattico.

È importante il principio:

> quando più quantità appartengono alla stessa analisi ma hanno funzioni cognitive differenti, il layout può essere composto da regioni coordinate invece di sovrapporre tutto nello stesso plot.

## 1.4 Mappa multiparametrica di pompa

La mappa delle pompe è uno dei benchmark più difficili.

Deve poter rappresentare simultaneamente:

- più curve `H(Q)` per differenti diametri di girante;
- iso-rendimento;
- iso-potenza;
- curva del circuito;
- Best Efficiency Point;
- Punto di Lavoro;
- annotazioni e valori numerici;
- legenda o labeling non ambiguo.

Questo benchmark serve a dimostrare che il sistema non produce soltanto line chart semplici.

## 1.5 Schema P&ID / processo

Lo schema della stazione di pompaggio mostra un'altra grammatica:

- apparecchiature riconoscibili;
- linee di processo;
- verso del flusso;
- strumenti;
- valvole;
- tag;
- quote e condizioni operative;
- layout lineare leggibile.

Non deve essere generato come un generico diagramma a rettangoli se la semantica richiede simboli di processo.

## 1.6 Grafico NPSH

Il grafico cavitazione mostra l'utilità di:

- due curve fisicamente differenti;
- soglia di sicurezza;
- punto di progetto;
- area di rischio;
- annotazioni;
- region shading controllato;
- takeaway immediato.

La regione colorata non è decorazione: rappresenta una condizione fisica.

# 2. Principio di progettazione: SVG-first, scientific-truth-first

La strategia preferita è:

```text
structured scientific meaning
→ deterministic or controlled rendering
→ SVG
→ verification
→ PDF
```

Non:

```text
LLM
→ stringa SVG improvvisata
→ speranza
```

## 2.1 SVG-first

Per visuali ricostruibili in modo affidabile, preferire SVG perché:

- è vettoriale;
- mantiene qualità in PDF;
- consente ispezione del DOM grafico;
- permette text measurement;
- permette QA geometrico;
- è versionabile;
- può essere rasterizzato in preview;
- può essere scaricato;
- può essere riutilizzato.

## 2.2 Non SVG-at-all-costs

Se una figura source-exact è troppo complessa o rischiosa da ricostruire:

```text
SOURCE_EXACT raster/vector source
> SVG scientificamente falso
```

La verità scientifica ha priorità sulla uniformità grafica.

# 3. Pipeline di rendering desiderata

La pipeline finale dovrebbe essere equivalente a:

```text
VisualCommitment
      ↓
VisualSpec
      ↓
Renderer Selection
      ↓
Renderer Input Validation
      ↓
SVG Draft
      ↓
SVG Normalize / Sanitize
      ↓
Geometry Measurement
      ↓
Preview Render
      ↓
Deterministic QA
      ↓
Scientific / Semantic QA
      ↓
Layout QA in target width
      ↓
Artifact Versioning
      ↓
Document Binding
      ↓
PDF Render
      ↓
Post-render QA
      ↓
FINAL
```

Anti-Gravity può progettare una pipeline differente se raggiunge meglio lo stesso end state.

# 4. VisualSpec: il modello non deve disegnare coordinate a caso

Il VisualSpec dovrebbe descrivere **significato e vincoli**, non necessariamente coordinate finali.

Esempio concettuale:

```json
{
  "id": "V034",
  "type": "CONCEPT_MAP",
  "purpose": "chapter_orientation",
  "title": "Architettura didattica dei modelli cinetici",
  "nodes": [
    {
      "id": "n1",
      "role": "root",
      "label": "Fenomeno",
      "subtitle": "La velocità cresce con T"
    }
  ],
  "edges": [
    {
      "from": "n1",
      "to": "n2",
      "relation": "explained_by"
    }
  ],
  "layoutIntent": "top_down",
  "importance": "HIGH",
  "target": {
    "medium": "A4_PDF",
    "maxWidthMm": 170
  }
}
```

Il renderer determina:

- coordinate;
- curve delle frecce;
- wrapping;
- box sizes;
- spacing;
- viewBox.

# 5. Eccezione: coordinate scientifiche vere

Per un grafico quantitativo, le coordinate derivano dai dati.

Esempio:

```text
data domain
→ scale
→ plot coordinates
```

Qui l'LLM non deve decidere le posizioni dei punti.

# 10. SVG contract

Ogni SVG finale dovrebbe rispettare un contratto minimo.

## 10.1 Deve avere

- `viewBox`;
- width/height coerenti o dimensionamento responsive;
- namespace valido;
- titolo/accessibility metadata quando appropriato;
- identificatore artifact;
- nessuno script;
- nessuna risorsa remota non controllata.

## 10.2 Deve evitare

- coordinate enormi arbitrarie;
- clipping accidentale;
- `foreignObject` non testato nel PDF engine;
- web fonts remoti;
- JS inline;
- filtri pesanti non necessari;
- riferimenti esterni fragili;
- path relativi non risolvibili.

---

# 11. SVG sanitization

Qualsiasi SVG proveniente da output LLM o source esterna deve essere considerato non affidabile.

Sanitizzare:

- `<script>`;
- event handlers;
- remote href;
- unsafe foreign content;
- invalid XML;
- ID collisions.

---

# 12. SVG normalization

Prima di salvare:

- normalizzare viewBox;
- garantire margine;
- deduplicare defs;
- stabilizzare ID;
- controllare transforms;
- verificare bounding box;
- controllare text overflow.

---

# 13. Tipografia

I grafici devono apparire come parte della dispensa.

Definire un sistema tipografico coerente.

## 13.1 Gerarchia minima

- title;
- subtitle;
- axis label;
- tick;
- annotation;
- legend;
- node title;
- node secondary text;
- caption esterna.

## 13.2 Minima leggibilità in PDF

Non ottimizzare sul browser a 200% zoom.

La dimensione deve essere giudicata alla larghezza reale nel PDF A4.

Definire una soglia minima verificabile.

Se il font scende sotto soglia:

```text
FAIL
```

oppure:

```text
re-layout / split
```

# 15. Math in SVG

Le formule devono mantenere qualità equivalente al LaTeX del documento.

Valutare:

- MathJax SVG;
- KaTeX + conversione;
- renderer matematico già presente;
- path;
- text + Unicode soltanto se sufficiente.

Il criterio è:

- correttezza;
- baseline;
- simboli;
- pedici;
- apici;
- greco;
- integrali;
- frazioni;
- scalabilità;
- PDF compatibility.

# 16. Color system

I visuali devono essere comprensibili anche quando:

- stampati;
- visualizzati con luminosità bassa;
- convertiti in scala di grigi quando necessario.

Il colore deve codificare significato.

Non affidare un'informazione soltanto al colore se può essere supportata anche da:

- line style;
- marker;
- label;
- pattern.

---

# 17. Colori semantici

Possibili ruoli:

```text
primary relation
secondary relation
source data
fit / model
warning
unsafe region
safe region
reference
derived
```

Non è necessario fissare qui valori HEX.

La palette deve essere coerente con il sistema editoriale.

# 18. Linee scientifiche

Definire:

- thickness minima;
- dash pattern;
- curve hierarchy;
- foreground/background;
- marker size.

Una mappa multiparametrica deve evitare che 20 curve abbiano tutte la stessa gerarchia visuale.

---

# 19. Axes

Per grafici quantitativi:

- unità sempre esplicita;
- nome grandezza;
- scale corrette;
- zero quando fisicamente significativo;
- range non ingannevole;
- ticks leggibili;
- scientific notation controllata.

---

# 20. Error bars / confidence

Quando presenti nei dati o richieste dal modello:

- devono essere vere;
- non decorative;
- basate su dati disponibili;
- annotate.

---

# 21. Regions and panels

Gli esempi dimostrano che StudyGenius deve supportare figure composte.

Esempio:

```text
┌────────────────────┬──────────────┐
│ main scientific    │ model result │
│ plot               │ panel        │
├────────────────────┴──────────────┤
│ residual diagnostics              │
└───────────────────────────────────┘
```

Il sistema deve poter comporre layout multipannello senza sovrapposizioni.

---

# 22. No overlay chaos

Se annotazioni, risultati e diagnostica rendono il plot illeggibile:

- creare pannelli;
- creare callout;
- spostare legenda;
- usare leader line.

Non sovrapporre riquadri neri o box che coprano i dati.

---

# 23. Leader lines

Le leader lines devono:

- partire dall'oggetto corretto;
- non attraversare testi inutilmente;
- non coprire punti chiave;
- terminare chiaramente.

---

# 24. Concept map layout

Il layout deve essere calcolato.

Non chiedere all'LLM di mettere spazi.

Possibili layout intents:

- top-down;
- left-right;
- radial;
- layered;
- swimlane;
- bifurcation.

La scelta dipende dalla semantica.

# 29. Multi-parametric plot

# 30. Label collision

Nessuna label importante deve sovrapporsi.

Possibili strategie:

- label placement algorithm;
- candidate positions;
- leader line;
- offset;
- hide low-priority label;
- split panel.

Ogni label nascosta deve essere giustificata.

# 33. Tagging

# 34. Source reconstruction

Se un grafico della fonte deve essere ricostruito:

1. estrarre struttura;
2. estrarre dati quando disponibili;
3. ricostruire;
4. confrontare;
5. verificare scientificamente;
6. registrare provenance.

---

# 35. Non inventare dati per “abbellire”

Se la fonte non fornisce un dato:

- non inventare una curva;
- non inventare error bars;
- non inventare valori;
- non inventare efficienze.

Un visuale pedagogico inventato deve essere classificato correttamente come MODEL_SIMULATED.

# 128. Final directive

Non considerare completato il sottosistema perché sai produrre un grafico bello.

Consideralo completato soltanto quando:

```text
StudyGenius identifies a visual need
→ creates the correct VisualSpec
→ selects the correct renderer
→ generates a valid SVG or justified fallback
→ persists it
→ provides a preview
→ inserts it into the correct Block
→ renders it correctly in the PDF
→ verifies it
→ can recover/export the artifact
→ documents the entire process
```

Questa specifica deve trasformare gli esempi “belli ma isolati” in **capacità affidabili di produzione**.

Il problema da risolvere non è più:

> “StudyGenius sa fare un SVG bello?”

Il problema è:

> **“StudyGenius sa produrre automaticamente, in modo ripetibile, verificabile e documentato, il visuale scientifico corretto ogni volta che la conoscenza lo richiede?”**

Solo quando la risposta è sì, il lavoro è concluso.
